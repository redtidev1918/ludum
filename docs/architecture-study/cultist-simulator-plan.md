## 1. 背景与目标

### 1.1 你在做的事
- 你手头有《Cultist Simulator》（《密教模拟器》）的 Android APK：包名 `com.playdigious.cultist`，
  Unity 引擎（IL2CPP），v3.9，Playdigious 发行。
- 你的库 `ludum`：**引擎无关、强类型 TS 的可复用玩法系统**（ECS、Resource、StateMachine、
  加权随机、保底、对话、条件、几何、交互）。**零运行时依赖、纯逻辑层**。
- **意图**：不是偷代码，是想**学习这款著名卡牌叙事游戏的核心玩法系统如何设计**，用它的
  **架构思想**来优化 gedum 自己的模块。

### 1.2 为什么《密教模拟器》值得学
它本质是一个**「卡牌 * 事件 * 状态机 * 资源 * 叙事」** 为核心的桌面游戏，逻辑密集、渲染轻。
其设计哲学与 ludum 高度同层：
- 大量**可组合的玩法原语**（卡牌、牌堆、时辰/时间推进、事件触发、资源消耗、条件、随机抽取）
- **数据驱动**：大量玩法由数据/定义驱动，而非硬编码逻辑
- **状态机 + 事件流**组织回合推进

这些都是 ludum 想覆盖的方向。反向提取它怎么组织这些系统，能直接指导 ludum 的模块演化。

## 3. 学习与落地方法论（重要：不照抄代码）

### 3.1 层次
逆向回来的是「可读反编译 C#」，不是原始源码。我们**取三层**：
1. **数据层**：卡牌定义、事件表、状态、资源值 —— 看它「用数据建模玩法」的方式。
2. **逻辑层**：状态机转移、事件触发、回合推进、抽取/洗牌算法 —— 看它「流程组织」。
3. **架构层**：模块边界、`Definition` vs `Runtime`、依赖注入、可扩展点 —— 看它「如何在
   不硬编码的情况下做大量内容」。（这一层对 ludum 最有价值。）

### 3.2 流程
1. **反编译**（工具层面，非 coding）：得到 `dump.cs` 全量类型和方法签名。
2. **定位核心系统**：用关键词锁定它最像 ludum 的部分（card/event/round/resource/state/random）。
3. **精读 + 画图**：对这几个核心系统画出「数据流 + 状态机」，写设计笔记。
4. **映射到 ludum**：把设计笔记里的**模式**（不是代码）翻译成对 ludum 的改进建议。

## 4. 期望从它身上提取的设计点（映射到 ludum）

这是**初步清单**，反编译后按实际标记增删。每一项都链到 ludum 的现有模块做「差距分析」。

| # | 学到的可能设计 | ludum 对应模块 | 潜在改进方向 |
|---|---|---|---|
| D1 | **数据驱动的卡牌/条目定义**（Definition 描述不可变规则） | `definition.ts` · `resource.ts` | 强化 `DefinitionRegistry`，观察它如何把大量内容做成纯数据 |
| D2 | **事件/触发系统**（当满足条件时触发效果） | `signal.ts` · `condition-expression.ts` | 看它事件如何条件化、如何避免硬编码链路 |
| D3 | **回合/时间推进状态机**（时辰制，一轮轮推进） | `state-machine.ts` · `clock.ts` | 对标它的回合状态机如何干净地表达复杂转移 |
| D4 | **加权随机 + 保底/抽取**（卡牌抽取、稀有度） | `weighted/` · `shuffle-bag.ts` | 对照它的抽取算法，是否有 ludum 没覆盖的场景 |

| D6 | **存档/序列化一致性**（Definition 与 Runtime 如何持久化） | 快照(ecs/resource) | 对标它的存档分层，补 ludum 的序列化缺口 |

## 5. 落地原则（红线）

1. **只提取设计，不复制代码文本**：ludum 中出现的任何实现都不照抄 Cultist 的 C# 代码、卡牌文案、
   美术或数据结构。参照的是**架构思想**，产出是**你自己的 TS**。
2. **符合 ludum 现有架构纪律**（AGENTS.md）：
   - 核心 `src/gamelib` 零运行时依赖、引擎无关、仅 `ES2022`。
   - `Definition != Runtime`；纯算法 + 有状态外壳。
   - 注入 `RandomSource` / `Clock`，游戏逻辑不直接 `Math.random()` / `Date.now()`。
   - 不引入全局单例、DI、事件总线、装饰器、魔法。
   - 只有 ≥2 个真实使用才加抽象。
3. **Scope 纪律**：一个子系统只改一个子系统，发现别处问题记到 audit，不扩 scope。
4. **门禁**：任何落地改动过 `npm run check`。
